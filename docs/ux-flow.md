# 明思 UX Flow

## UX Principles

- App 应该像一个安静的思考工作台，而不是聊天窗口。
- 用户不应该先被迫整理大段口述文本，AI 先做低风险结构化。
- AI 负责整理、追问和建议，用户负责确认、取舍和验证。
- Daily loop 需要能在 10-15 分钟内完成。
- 进步应通过前后对照和真实证据展示，而不是通过虚假的分数。

## Primary Navigation

MVP 底部 Tab：

- 今日：完整日常闭环。
- 历史：过去记录、卡片、任务、验证和证据。
- 项目：抽象项目和当前阻塞。
- 成长：周/月报告、趋势和原则资产入口。
- 设置：隐私、GLM API Key、数据和通知。

导航规则：

- Tab 是功能区，不是流程步骤。
- Today 拥有完整状态机。
- 用户可随时切换 Tab。
- 未完成闭环自动保存，并在其他 Tab 显示 Resume Today banner。

## First-Time Setup

1. Welcome
   - 展示产品名：明思。
   - 展示 slogan：不替你思考，而是训练你把事情想清楚。

2. Privacy Boundary
   - 用户确认不输入公司文档、代码、客户名或内部数据。
   - App 建议用 Project A、Team B 这类抽象命名。

3. GLM API Key
   - 用户输入自己的 GLM API Key。
   - Key 存入 Keychain。
   - 设置页可更新或清除。
   - 保存 Key、Base URL 或模型名后，App 立即发起一次连接测试。
   - 设置页显示当前连接状态；如果端点不支持 `response_format`，App 会自动重试兼容模式，并在失败时展示可读错误。

4. Training Goal
   - 选择 1-2 个目标：清晰度、价值判断、执行可靠性、项目判断、反思深度。

5. Active Projects
   - 创建抽象项目卡。

6. Baseline
   - 五项指标自评。

7. Default Mode
   - 默认 Standard。
   - 用户可改成 Quick 或 Deep。

## Today State Machine

```text
VerifyYesterday
Capture
Organizing
ReviewCards
SelectMode
SelectLens
AnswerQuestions
ReviewQuests
ExtractPrinciple
SessionComplete
```

全局交互规则：

- 顶部进度条既显示进度，也允许回到已完成步骤。
- 用户不能点到未来步骤；`Organizing` 是执行态，不作为返回编辑点。
- 回退到较早步骤后，后续派生内容会被清空并重新生成，界面必须明确提示“后续内容会在确认后重新生成”。
- 底部操作区在可回退时显示轻量“上一步”，避免流程变成单向隧道。
- ReviewCards 及后续步骤必须提供明确的“补充材料”入口。MVP 行为是追加原始输入、回到 Capture、清空后续派生卡片/问题/任务/原则，并由用户重新整理，避免新旧证据混杂。
- 视觉 token 必须支持系统暗色模式；不得混用固定深色文字和系统黑色背景。

AI 失败规则：

- AI 调用失败时，当前步骤显示失败原因和“重试当前步骤”。
- 初次失败时允许本地 fallback 先填充可编辑草稿，让用户继续走流程。
- 如果 fallback 被使用，App 顶部显示待补跑横幅，用户可点“后台重试”。
- 重试成功后，横幅计数减少；重试失败时保留现有内容并继续允许重试。
- 横幅关闭只隐藏待补跑提醒，不删除用户已确认内容。

流式整理规则：

- `organizeCards` 必须显示真实流式进度，而不是只有静态 spinner。
- 读取到 `<CARD>` 时，Today 立即显示一张临时候选卡。
- 读取到 `<TITLE>`、`<BODY>` 等字段时，临时卡逐步填充内容。
- 读取到 `</CARD>` 时，卡片显示完成标记，等待后续进入正式 Review。
- 如果流式中断但已有闭合卡片，用户可以继续查看已生成卡片，也可以重试当前步骤。
- 未闭合卡片不能进入后续追问或历史证据。

### VerifyYesterday

条件：

- 昨天存在 active main quest。

界面：

- 昨日主线任务。
- 完成状态：完成、部分、未完成。
- 实际价值：高、中、低、不明确。
- 未完成原因。

完成后进入 Capture。

### Capture

界面：

- 日期和当前状态。
- 大文本输入。
- Quick / Standard / Deep 分段控件。
- 隐私提醒。
- Save Draft。
- Organize。

输入方式：

- 键盘。
- iOS dictation。
- 第三方输入法语音输入。

### Organizing

界面：

- 流式卡片生成状态。
- 已生成卡片数量。
- 当前正在接收的临时候选卡。
- 已闭合卡片的完成标记。
- 不展示聊天流，只展示受控卡片组件。
- 如 GLM Key 缺失，引导去设置。

行为：

- 通过 GLM SSE 流式生成临时候选卡片。
- 如果模型完全失败且没有闭合卡片，生成本地 fallback。
- 如果模型中断但已有闭合卡片，保留闭合卡片，提示可以重试补全。

### ReviewCards

界面：

- 按类型分组的卡片。
- 每张卡片显示标题、正文、类型、重要度、敏感性。
- 操作：编辑、删除、合并、标记重要、标记敏感。
- 操作区显示“补充材料”，允许用户回到 Capture 追加一段输入并重新整理。

完成条件：

- 用户点击 Confirm Cards。

### SelectMode

如果用户在 Capture 已选择模式，此步骤仅作为确认。

模式差异：

- Quick：最少追问，快速生成主线任务。
- Standard：完整卡片、透镜、任务和原则候选。
- Deep：更多追问和反方质疑，用于重要事件。

### SelectLens

界面：

- 推荐透镜卡。
- 可手动切换。
- 每张透镜卡必须使用中文名称、简短方法说明和差异化视觉符号，避免用户只看到抽象英文概念。

MVP 透镜：

- 证据校验：区分事实、判断和假设。
- 反方视角：主动寻找相反证据。
- 杠杆分析：找出最能改变结果的一步。
- Execution Bias Check。

### AnswerQuestions

界面：

- 3-5 个问题卡。
- 用户至少回答一个。
- 问题必须具体、克制、不指责。
- 如果本次追问召回了历史 active 原则，在问题卡前展示“本次参考的原则”，并标明“仅作对照”。

Quick 模式：

- 1-2 个问题。

Standard 模式：

- 3 个问题。

Deep 模式：

- 4-5 个问题，并至少包含一个反方问题。

### ReviewQuests

界面：

- Main Quest。
- Side Quest。
- Observation Quest。
- 每个任务包含为什么重要、完成标准、预期阻力、反思问题。
- 如果本次任务生成召回了历史 active 原则，在任务列表前展示“本次参考的原则”，用户能判断任务是否被旧经验正确影响。

操作：

- 确认。
- 编辑。
- 删除次要任务。
- 设置本地提醒。

规则：

- Main Quest 必须有 completion criteria。
- 本地通知默认使用简洁标题，避免暴露敏感细节。

### ExtractPrinciple

界面：

- AI 最多提出 1 条行动准则候选。
- 用户可保存、修改或忽略。

原则卡内容：

- 标题。
- 适用场景。
- 具体做法。
- 成功标准。
- 来源日期。

### SessionComplete

界面：

- 明日主线任务。
- 今天训练的思维能力。
- 已保存的原则。
- 返回 Today 或查看历史。

## History Flow

目的：

- 作为成长和校准的证据层。

入口：

- History tab。
- Growth 证据卡。
- Project 相关记录。
- Verification 历史。

列表：

- 按日期分组。
- 顶部提供本地搜索和证据类型筛选，支持快速找到卡片、任务、验证、原则、项目链接和成长归因。
- 在本地搜索基础上提供细筛：项目、透镜、卡片类型和任务状态。细筛只从已加载历史证据派生，MVP 不保存筛选器、不做 AI 语义搜索。
- 展示状态、主线任务、透镜、验证状态和证据摘要。
- 日历使用小标识区分确认卡片、任务/验证、原则/总结，避免只有“有记录”的单一红点。

详情：

- 原始输入默认折叠。
- 确认后的卡片；未确认卡片只能作为待确认提示，不算作证据卡片。
- 透镜和回答。
- 明日任务。
- 次日验证。
- 原则候选或已保存原则。

## Project Flow

目的：

- 把分散的每日复盘聚合成长期议题。
- 让用户看见项目进展和项目中思考方式的变化。

Project 的含义：

- Project 是抽象工作流或长期议题，不要求等同于公司项目名。
- Project 可以是“会议效率”“某类跨团队协作”“判断质量训练”“某个长期目标”。
- Project 不直接保存敏感原名，必要时使用用户确认的抽象名称。

入口：

- Project tab。
- Daily ReviewCards 中的项目关联建议。
- History 单日记录中的项目链接。
- Growth 指标证据中的项目链接。

项目创建：

1. 用户手动创建项目。
2. 或 AI 根据多日记录提出候选项目。
3. 用户确认名称、目标、成功标准和隐私安全命名。
4. 项目进入 active 或 watching 状态。

项目候选确认页：

- 显示候选名称、目标、当前阻塞、成功标准。
- 显示“为什么建议创建”：最多 3 条来源证据。
- 显示“为什么不是普通标签”：长期目标、重复阻塞或持续行动标准。
- 用户动作：创建、改名后创建、暂时忽略、拒绝此类建议。

项目关联：

- 每日卡片确认后，AI 可建议关联到 0-2 个项目。
- 用户可以接受、拒绝或手动选择项目。
- 未确认卡片不能自动成为项目证据。
- 敏感卡片默认不进入项目摘要，但可保留本地链接。
- 关联建议出现在 Card Review 之后，不阻塞 Today 主流程。
- 用户跳过关联建议时，记录保持在 History 中，但不进入 Project timeline。

项目合并：

- 系统展示 Merge Candidate。
- 展示两个项目的目标、阻塞、最近证据和合并理由。
- 用户可选择合并、保持分开或稍后提醒。
- 合并后保留来源关系，不删除历史证据。

Project tab 信息架构：

- 顶部：Active / Watching / Paused / Archived 分段筛选。
- 列表：项目名、当前目标、当前阻塞、最近证据、next bet、最后更新日期。
- 右上角：候选队列入口，显示待确认项目和合并建议数量。
- 项目详情：
  - Overview：目标、成功标准、当前阻塞。
  - Timeline：关联 DailyEntry、Quest、Verification。
  - Thinking Change：早期/近期对同类问题的定义差异。
  - Open Questions：仍未解决的关键问题。
  - Principles：在该项目中形成或验证的原则。

Project detail 跳转规则：

- Timeline 中每条记录都能跳到 History day detail。
- Progress signal 能跳到对应 Quest、Verification 或 ThinkingCard。
- Thinking Change 的 before 和 after 分别跳到两条来源证据。
- Principle 能跳到 Principle source record。

项目进展展示：

- 最近一周完成的主线任务。
- 关闭的开放问题。
- 阻塞变化。
- 新增风险。
- 下一个最值得验证的问题。

项目进展交互：

1. 用户进入 Project detail。
2. 首屏显示 current goal、current bottleneck、next bet。
3. 下方按时间展示 progress signals，而不是百分比。
4. 点击 signal 展开来源证据和 AI 判断理由。
5. 用户可以标记“不准确”，该条 signal 降级为 dismissed，不再用于 Growth 归因。

项目思考变化展示：

- Before/After 对照。
- 例：从“推进项目”变成“确认当前阻塞是边界问题还是设计问题”。
- 每个变化必须链接到历史证据。

思考变化交互：

1. 系统只在存在 before 和 after 证据时展示。
2. UI 左侧显示早期表述，右侧显示近期表述。
3. 中间或下方显示变化解释：问题定义、证据意识、价值判断或执行可靠性发生了什么变化。
4. 用户可以保存为 PrincipleAsset，或标记为“还没有形成稳定能力”。

项目候选交互：

1. 用户在 Today 卡片确认后看到最多 2 个关联建议，但不被迫处理。
2. 用户也可以从 History day detail 手动创建候选项目。
3. 候选详情展示建议名称、目标、阻塞、成功标准和来源证据。
4. 用户选择创建、改名后创建、暂时忽略或拒绝。
5. 拒绝后同类候选进入冷却，不再反复打扰用户。

## Growth Flow

展示：

- 周度校准。
- 月度成长。
- 五项趋势指标。
- 前后对照。
- 证据链接。
- 原则库入口。

Growth 不能展示没有证据来源的结论。

Growth 交互：

- 总览页显示五项指标当前值、上期值和变化箭头。
- 点击任一指标进入 Metric Detail。
- Metric Detail 展示：
  - 当前分数。
  - 上期分数。
  - 变化量。
  - 为什么变化。
  - 本期加分事件。
  - 本期减分事件。
  - 证据链接。
  - 下一个训练建议。

Growth 总览降级规则：

- 完整闭环少于 3 次：不显示数值仪表，只显示“证据收集中”和已完成闭环数量。
- 指标没有正/负贡献事件：显示趋势未知，不显示孤立分数。
- 指标有贡献事件但证据冲突：显示“待校准”，引导用户查看冲突证据。

贡献事件：

- 每个加分/减分事件都来自明确证据。
- 事件来源包括 DailyEntry、ThinkingCard、Quest、Verification、PrincipleAsset。
- 用户点击贡献事件，跳到对应历史记录。
- 用户可以把贡献事件标记为“不准确”；该反馈进入下次报告的校准上下文。

分数解释：

- 不展示没有解释的数字。
- 不使用“你变聪明了”这类人格判断。
- 用行为证据解释趋势，例如：
  - “主线任务完成标准比上周更具体。”
  - “两次任务完成但实际价值低，说明价值判断需要校准。”
  - “连续三次能主动写出反方证据，反思深度提高。”

成长闭环：

1. Daily 产生证据。
2. Verification 产生结果。
3. Weekly/Monthly 汇总趋势。
4. Growth 解释指标变化。
5. 用户选择下期训练重点。
6. Today 根据训练重点推荐透镜或追问方式。

Metric detail 跳转闭环：

1. Growth overview -> 点击指标。
2. Metric detail -> 点击加分或减分事件。
3. Source detail -> 进入 History day detail，并高亮对应卡片、任务或验证。
4. 用户返回 Growth 后，可以接受解释、标记不准确，或把它加入下期训练重点。

Metric detail 必须展示一条可解释路径：

```text
当前值
-> 上期值
-> 本期正向贡献
-> 本期负向贡献
-> 不确定或冲突证据
-> 下周训练建议
```

当用户问“为什么是这个数”时，界面回答的是贡献账本，而不是模型总结。

## Settings Flow

设置项：

- GLM API Key。
- 默认模式。
- 本地通知。
- 隐私边界。
- AI 调用审计：最近 Prompt 调用、成功/失败、模型、source/context 数量、失败原因。
- 数据导出。
- 数据清除。
- 外观密度。

## Guardrails

- 用户可以离开流程，但不能跳过关键确认。
- 未确认卡片不能作为最终事实源。
- 敏感卡片默认不进入后续模型调用。
- AI 生成任务必须由用户确认才激活。
- 原则候选必须由用户确认才进入原则库。

# 职场表达：一个主旨，分组理由

**状态：基于作者官方概念说明的局部提炼草稿，不是整本《金字塔原理》完成拆书。** 蓝本和版本区别见[来源](references/sources.md)。

## 何时使用

用户需要写汇报、提案、邮件，或一段话信息很多但主旨不清。用户只是分享感受或希望保留文学表达时不强制套用。先按需要给草稿，不让用户先学会术语。

## 方法

- 确定读者需要回答的那个问题；区分“目前发生什么”和“希望对方作出什么决定”。后者只有用户确有请求时才加入。
- 根据实际材料形成一个可支持的核心判断。没有足够依据就用“当前状态／待确认”，不能为了结论先行硬造结论。
- 把相关事实和理由分组，检查同组是否真正支持上层判断、是否有缺口或重复；不为凑固定三点拆分。
- 按用户场合组织：可先给主旨再解释理由，也可先交代必要背景。需要引出问题时参考情境—变化／复杂之处—读者疑问，避免把事实串成无关时间流水账。
- 如用户有明确请求，保留请求对象、事项与已有期限；未提供的金额、日期和承诺不得补造。

## 产物与完成

用户要改写时先交一版可直接使用的文本，必要时补一句结构调整原因。分析请求才说明组织逻辑。读者能辨认核心判断、依据及需要回应什么，即完成；简短不等于删掉坏消息、风险或不同意见。

合成例（输入已提供事实）：两个接口尚未联调，原计划周五发布，用户想向负责人申请延到周一。输出应围绕延期请求和接口风险组织，不编造预计修复小时数，也不把延期写成已经批准。

“结论—依据—请求”是明思的场景适配；请求不是原书所有文体都必须有的固定段落。

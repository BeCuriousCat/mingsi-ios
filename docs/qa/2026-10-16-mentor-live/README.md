## 当前结论

设备已保存密钥，且此前真实 GLM 调用成功；当前账户错误仍阻塞后续验收。当前最大的产品问题是合法 JSON 与有效引导之间的落差：材料不足仍急着教学、把并列事项猜成因果、一个回应索取多份答案。2.11.0 自动检查通过，但逐条 AI 复核拒绝该版；不能用测试数替代回答质量。

当前代码为 `mentorRespond` **2.12.0**，理解草稿仍为 **2.6.0**。2.12.0 本地协议和生产请求快照检查通过，但三次真实尝试均未取得模型回答。最后一次已明确取得 **HTTP 429 / 业务码 1113**；官方定义为“余额不足或没有对应资源包”。因此当前状态是 **真实语义待验收，账户余额或资源包待用户处理**，没有新版语义通过结论。

用户随后确认已处理 API Key，恢复一次真实请求，仍在第一个合成场景收到 **429 / 1113**，没有取得模型正文。设备保存的配置仍为 `api.z.ai` / `glm-5.3`，本次证据见 [恢复请求](evidence/v2120-resumed-quota/manifest.json) 与 [错误摘要](evidence/v2120-resumed-quota/service-failure.json)。这使 2.12.0 累计四次真实尝试均未获得回答；确认后没有重试、换模型或切换接口。另一次启动因临时 xctestrun 路径破坏产品相对路径而失败，未发出模型请求，未计入四次调用。

## 配置检查更正

旧 Alpha 预检读取的是 Mac 钥匙串；模拟器检查又只比较明文 service/account，未识别当前 20 字节 SHA-1 索引，产生了假阴性。此前 SQL 记录为 0 不能证明用户没有保存密钥。历史设备测试明确报告跳过的那次仍是当次事实，不能据此外推后续状态。

预检现只读取指定模拟器的 service/account 索引元数据，兼容文本、UTF-8 与 SHA-1；不读取密钥内容。当前真实 hosted test 已从模拟器 Keychain 读取配置并成功调用模型。后来的 1113 是服务端账户/套餐问题，不是缺少 Key。

### 后续本地审查：停止边界、引用与上下文冲突

在账户问题待处理期间，继续检查实际生产链路，发现并修复三处可由本地证据确认的问题：

1. `CoachAnswerReviewAIService` 原校验允许 `user_boundary=stop` 与非空 `next_repair_question` 同时通过。现在任何准备度下的 stop 都必须为空追问；拒绝矛盾响应，不替模型改写答案。
2. 原允许引用集合包含事项 ID，导致仅引用事项身份或将其混入有效回答引用也会被接受。现在只允许确认卡片和非空回答 ID；`currentCase.evidenceRefs` 同样排除事项自身 ID，请求追踪仍保留事项身份。
